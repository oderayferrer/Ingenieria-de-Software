
[[Plantilla Casos de Uso]]
## Parte I: Definiciones generales

**a) Describa qué es el desarrollo centrado en el usuario.**
El desarrollo centrado en el usuario es un enfoque en la ingeniería de requerimientos que coloca las necesidades, expectativas y objetivos de los usuarios finales en el centro del diseño y especificacion del software. A traves de las tecnicas como los Casos de Uso, se busca capturar y entender los requerimientos funcionales desde la perspectiva explicita del actor o usuario que interactua con el sistema. Esto facilita un lenguaje comun entre desarrolladores y stakeholders, fomentando la participacion activa del cliente y reduciendo el riesgo de rechazo del sistema

**b) Defina qué son los casos de uso y describa cómo se utilizan.**
**Definición**: Un Caso de Uso es una técnica de especificación de requerimientos que describe como los distintos actores (personas, otros sistemas o eventos temporales) interactúan con el sistema para lograr un objetivo funcional especifico. Representa una funcionalidad individual y delimita la secuencia de actividades e interacciones entre el actor y el sistema
**Como se utilizan**: Se emplean para descomponer el alcance global del sistema en piezas mas pequeñas y manejables. El proceso de modelado de Casos de Uso se realiza en 4 pasos generales:
1. Identificar los actores que interactuan con el sistema
2. Identificar los casos de uso correspondientes a los requerimientos funcionales
3. Construir el diagrama de casos de uso para ilustrar las relaciones entre actores y funcionalidades
4. Realizar los escenarios (narraciones textuales estructuradas de cada caso de uso)

c) Defina qué es un actor y un escenario.
**Actor**: es toda entidad externa que interactua directamente con el sistema para inicar una actividad o recibir un resultado. Representa un rol desempeñado frente al sistema y puede clasificarse en:
- Persona
- Sistema o subsistema externo
- Dispositivo externo
- Tiempo (Actúa únicamente como disparador automático de eventos programados ej. procesos semanales o nocturnos)

**Escenario**: Es la descripción detallada y narrativa en texto de la secuencia de pasos e interacciones entre el actor y el sistema para completar la funcionalidad del caso de uso. Su estructura formal incluye:
- Nombre del CU: Debe iniciar con un verbo en infinitivo que represente la meta
- Descripción: Propósito general del CU
- Actores: Entidades involucradas
- Precondiciones: Restricciones del estado del sistema asumidas como verdaderas antes de iniciar la ejecucion (a menudo la postcondicion de otro CU)
- Curso Normal: Secuencia numerada de pasos del "camino feliz" (sin errores ni excepciones)
- Curso Alterno: Descripcion del comportamiento en caso de excepciones, variaciones o errores durante el flujo tipico
- Postcondición: Estado en el que queda el sistema tras la finalizacion exitosa

d) Defina las relaciones que pueden presentarse en el diagrama de casos de uso. Describa cuándo se utiliza cada una.
- Asociación: 
	- Definición: Es la relacion basica entre un actor y un caso de uso que interactuan entre si
	- Cuando se utiliza: Cuando un actor inicia un caso de uso o cuando el caso de uso requiere enviar/recibir información directa con ese actor
- Uso o Inclusion (`<<uses>>/ <<include>>`): 
	- Definición: Es una relación dirigida desde un CU base hacia otro CU, donde el CU base incluye obligatoriamente la ejecución del CU incluido
	- Cuando se utiliza: Para reducir la redundancia y evitar duplicación de lógica, extrayendo pasos o comportamientos comunes compartidos entre dos o mas casos de uso. Regla de la catedra: Un caso de uso incluido debe ser accedido al menos por dos casos de uso distintos
- Extension(`<<extends>>`): 
	- Definición : Relación dirigida desde el CU extendido hacia el CU base, donde la funcionalidad del CU extendido se suma al CU base, unicamente si se cumple una condición o excepción determinada
	- Cuando se utiliza: Para modelar flujos opcionales, especiales o de excepción que amplían la funcionalidad del caso de uso original pero que no necesitan ejecutarse obligatoriamente siempre
- Herencia (Generalización entre Actores):
	- Definición: Relación entre actores donde un actor hijo asume o hereda las funciones y asociaciones de uno o mas actores padre (actor resumen)
	- Cuando se utiliza: Cuando dos o mas actores comparten un conjunto común de casos de uso, extrapolando ese comportamiento a un actor generalizado para simplificar el diagrama y reducir asociaciones redundantes

e) Enumere los beneficios de modelar requerimientos del sistema con casos de uso.
- Captura efectiva de requerimientos funcionales: Permite expresar claramente lo que el sistema debe hacer desde el punto de vista del negocio
- Descomposición del alcance: divide el sistema en módulos y piezas de trabajo mas manejables
- Medio de comunicación fluido: Utiliza un lenguaje sencillo e intuitivo fácil de entender tanto por clientes/usuarios como por el equipo técnico
- Estimación de esfuerzo y alcance: Ayuda a estimar los tiempos, costos y recursos necesarios para el desarrollo
- Linea base para pruebas: Proporciona la estructura sobre la cual el equipo de pruebas (QA) diseña los planes y escenarios de prueba de validación 
- Linea base documental: Sirve de guia para elaborar el resto de la documentación tecnica y del usuario
- Trazabilidad: Facilita el seguimiento de los requerimientos a lo largo de todo el ciclo de vida del software

Flecha vacia -> herencia
Flecha llena -> Inicializa un CU
Flecha sin punta -> Interactua pero no lo dispara

Extends -> Un solo CU hace uso de otro
Uses -> Si dos casos de uso utilizan un CU es USES

### 1. Alquiler de mobiliario

Suponga que trabaja en una consultora la cual ha sido recientemente contactada por una empresa de alquiler de mobiliario para eventos para la realización de una app.
De las diferentes entrevistas se ha obtenido la siguiente información:
El gerente nos dijo que resulta fundamental tener una aplicación móvil que nos permita manejar la agenda de la empresa, sabiendo qué disponibilidad tenemos y permitiendo que nuestros clientes alquilen a través de la app.
Para esta primera versión de la app, el gerente nos pidió que sea posible dar de alta los diferentes mobiliarios, así como la posibilidad de que los usuarios puedan realizar una reserva de alquiler desde sus dispositivos. Para el detalle de cómo se realiza la carga de los muebles, el gerente nos sugirió hablar con el encargado del departamento de mobiliario. El encargado de mobiliario nos comentó que de cada mueble se debe cargar código de inventario, tipo de mueble, fecha de creación, fecha de último mantenimiento, estado (libre, de baja, alquilado) y el precio de alquiler. Además, no pueden existir códigos repetidos. Para que el encargado pueda dar de alta el mobiliario debe autenticarse en el sistema. El registro de los usuarios de carga no debe modelarse. 
El encargado del departamento de alquileres no comentó acerca de las reservas de los alquileres. Por una política comercial de la marca una reserva tiene que incluir como mínimo 3 muebles. La reserva debe tener una fecha, lugar del evento, cantidad de días y mobiliario junto a su cantidad. Para realizar una reserva se debe abonar el 20% del total del alquiler. El pago de la reserva se realiza únicamente con tarjeta de crédito validando número de tarjeta y fondos a través de un servicio del banco. Luego de efectuado el pago, se emite un número de reserva único que será luego utilizado por el cliente para hacer efectivo el alquiler.

Actores:
	Encargado de mobiliario: Actor primario que interactúa con el sistema para dar de alta los muebles en el inventario
	Cliente: Actor primario que realiza la reserva del mobiliario para un evento a traves de la app móvil
	Servicio del  Banco: Actor secundario/sistema externo que valida los datos de la tarjeta de credito y la disponibilidad de fondos durante el pago del 20%
Casos de uso:
- **Iniciar sesión**
- **Cerrar sesión**
- **Registrar mueble**
- **Reservar alquiler**
- **Pagar con tarjeta**

## 2. Posgrado

Suponga que trabaja en el área de sistemas de la Facultad de Informática y se le solicitó la automatización del ==pago de carreras de posgrado==. Inicialmente se coordinó una reunión con el director del posgrado y se obtuvo la siguiente información:
Ya que no se desea seguir cobrando el dinero en la secretaría, es necesario que los ==🟠alumnos== puedan pagar las carreras vía web. Como el director de posgrado no realiza tareas administrativas nos recomendó hablar con el secretario académico.
De la entrevista con el secretario académico se obtuvo la siguiente información:
Es necesario ==cargar las carreras a un sistema.== En esta primera versión del sistema sólo se nos pidió esta funcionalidad, ==sin la modificación ni eliminación.== De cada carrera se conoce: ==nombre de la carrera (no puede repetirse), duración en años (a partir de la consulta del estatuto de posgrado se obtuvo que como máximo son 5 años), costo y cantidad máxima de cuotas para el pago==.  La carga de las carreras no la realiza el secretario académico sino un ==🟠empleado administrativo==.
Al preguntarle por la dinámica del sistema, el secretario académico nos derivó con el jefe del área administrativa, con el cual hicimos otra entrevista y pudimos obtener la siguiente información:
El requerimiento fue que el ==alumno ingrese a la web de posgrado y pueda registrarse ingresando: nombre, apellido, nombre de usuario (único) y contraseña (más de 6 dígitos). ==
Cualquier alumno previamente registrado, puede ==🟢iniciar sesión== con su nombre de usuario y contraseña, habilitándose la ==🟢inscripción== a alguna de las carreras.
Para ejemplificar esta funcionalidad nos otorgaron acceso al sistema SIGEF, el cual realiza funcionalidades similares para las carreras de grado.
Para inscribirse, el alumno deberá seleccionar ==la carrera, ingresar la cantidad de cuotas a pagar, ingresar el número de tarjeta y, en caso de que la tarjeta sea válida y tenga fondos, se hará efectivo el cobro y la inscripción.==
La tarjeta de crédito ==se valida a través de un servicio del banco== con el cual la universidad tiene convenio. Luego de efectuado el cobro, el sistema debe imprimir dos comprobantes, uno de inscripción y otro de pago. La única
forma que tiene el alumno de pagar es con tarjeta de crédito.

Los ==🟢usuarios== deben estar registrados y contar con una tarjeta para los pagos. Para ==🟡registrarse== , un usuario concurre a una dependencia municipal donde un ==🟢empleado== o el responsable del área lo da de alta, pidiéndole los datos personales y el número de tarjeta.

El sistema calcula el monto y se conecta a un servidor de pago pasando el monto, el nombre del usuario y el número de tarjeta. Para devolver la bicicleta, el usuario apoya la tarjeta en el lector y si la misma pertenece a un usuario registrado libera el receptor durante 45 segundos. Si el usuario no pone la bicicleta, se cancela la operación. Si se detecta la bicicleta se procede al cobro del alquiler. El sistema calcula el monto y se conecta a un servidor de pago pasando el monto, el nombre del usuario y el número de tarjeta. De haber algún problema con el alquiler o devolución de la bicicleta debe informarse en el display.
